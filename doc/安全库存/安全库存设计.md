# 安全库存 - 退货关联表设计方案（v5.0）

---

## 一、需求概述

### 1.1 业务背景
根据 `sales_order_history` 表中的订单数据，建立常规订单（order_type_id=1）与退货订单（order_type_id=2）的关联关系，用于安全库存计算和销售数据分析。

### 1.2 数据规模
- **数据来源**：`sales_order_history` 表
- **时间范围**：2024-01-01 ~ 2026-07-24
- **总记录数**：263,657 条
- **估算退货订单比例**：约 8-12%（约 21,000 ~ 31,600 条）

### 1.3 核心业务规则

| 规则编号 | 规则描述 |
|---------|---------|
| R1 | 常规订单与退货订单通过 `customer_id` + `number`(OE) + `brand_name` + `pdname` + `frey_no` 进行匹配 |
| R2 | **去掉price匹配条件**，避免优惠折扣影响匹配 |
| R3 | **多对多匹配**：一条退货订单可匹配多条常规订单，一条常规订单也可被多条退货订单匹配 |
| R4 | **数量分摊**：退货订单数量分摊到常规订单，直到退货数量用完；常规订单数量分摊到退货订单，直到数量用完 |
| R5 | 常规订单被部分匹配后，剩余数量可继续参与后续匹配 |
| R6 | 按时间顺序处理退货订单，先处理时间靠前的 |

### 1.3 Type类型定义（v5.0）

**编码规则：**
- **十位（第一位）**：匹配状态分类
- **个位（第二位）**：匹配模式（1=一对一，2=一对多-常规订单视角，3=一对多-退货订单视角）

| type值 | 含义 | 触发条件 |
|--------|------|---------|
| 01 | 其他异常 | 不属于其他类型的异常情况 |
| 11 | 完全退货（一对一） | processed_quantity = 0，一对一匹配 |
| 12 | 完全退货（一对多-常规订单） | processed_quantity = 0，一条常规订单被多条退货订单分摊完 |
| 13 | 完全退货（一对多-退货订单） | processed_quantity = 0，一条退货订单分摊到多条常规订单后用完 |
| 21 | 部分退货（一对一） | processed_quantity > 0，一对一匹配，常规订单有剩余 |
| 22 | 部分退货（一对多-常规订单） | processed_quantity > 0，一条常规订单被多条退货订单分摊后仍有剩余 |
| 23 | 部分退货（一对多-退货订单） | processed_quantity > 0，一条退货订单分摊到多条常规订单后常规订单仍有剩余 |
| 31 | 退货数量超出（一对一） | processed_quantity < 0，一对一匹配，退货数量未完全抵消 |
| 32 | 退货数量超出（一对多-常规订单） | processed_quantity < 0，一对多匹配场景 |
| 33 | 退货数量超出（一对多-退货订单） | processed_quantity < 0，一条退货订单分摊到多条常规订单后仍有剩余 |
| 40 | 未匹配 | 退货订单匹配未找到符合条件的常规订单 |
| 50 | 未进行匹配 | 新入库的退货订单，尚未进行匹配处理 |

## 二、表结构设计

### 2.1 退货关联表 `stock_safe_refund_ref`

```sql
CREATE TABLE IF NOT EXISTS `stock_safe_refund_ref` (
    `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    `normal_order_items_id` INT DEFAULT NULL COMMENT '常规订单明细ID（sales_order_history表orders_items_id），未匹配时为NULL',
    `refund_order_items_id` INT NOT NULL COMMENT '退货订单明细ID（sales_order_history表orders_items_id）',
    `oe` VARCHAR(255) DEFAULT NULL COMMENT 'OE号（退货订单对应的number字段）',
    `brand_name` VARCHAR(255) DEFAULT NULL COMMENT '品牌名（退货订单对应的brand_name字段）',
    `product_name` VARCHAR(255) DEFAULT NULL COMMENT '产品名称（退货订单对应的pdname字段）',
    `barcode` VARCHAR(255) DEFAULT NULL COMMENT '条码（退货订单对应的frey_no字段）',
    `customer_id` INT DEFAULT NULL COMMENT '客户ID（退货订单对应的customer_id字段）',
    `product_price` DECIMAL(18, 4) DEFAULT NULL COMMENT '产品单价（退货订单对应的price字段）',
    `normal_total_price` DECIMAL(18, 4) DEFAULT NULL COMMENT '常规订单总价',
    `refund_total_price` DECIMAL(18, 4) DEFAULT NULL COMMENT '退货订单总价',
    `normal_quantity` INT DEFAULT NULL COMMENT '常规订单数量',
    `refund_quantity` INT DEFAULT NULL COMMENT '退货订单数量',
    `processed_price` DECIMAL(18, 4) DEFAULT NULL COMMENT '处理价格（常规订单total_price + 退货订单total_price）',
    `processed_quantity` INT DEFAULT NULL COMMENT '处理数量（常规订单quantity + 退货订单quantity）',
    `match_count` INT DEFAULT 0 COMMENT '匹配次数（用于判断是否为一对多匹配）',
    `type` TINYINT DEFAULT NULL COMMENT '类型（两位数编码：十位=匹配状态，个位=匹配模式）',
    `created_at` DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '数据创建时间',
    `updated_at` DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '数据更新时间',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_refund_normal` (`refund_order_items_id`, `normal_order_items_id`) COMMENT '退货订单+常规订单联合唯一，防止同一组合重复匹配',
    KEY `idx_customer_id` (`customer_id`),
    KEY `idx_oe` (`oe`),
    KEY `idx_type` (`type`),
    KEY `idx_normal_order` (`normal_order_items_id`) COMMENT '常规订单ID索引，用于快速查询某常规订单的所有匹配记录'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='安全库存退货关联表';
```

**索引说明：**
- `uk_refund_normal`：联合唯一索引，确保同一个退货订单+常规订单组合只存在一次
- `idx_normal_order`：常规订单ID索引，方便查询某常规订单的所有匹配记录

### 2.2 索引优化（sales_order_history 表）

```sql
ALTER TABLE `sales_order_history` ADD INDEX `idx_match_refund` (
    `customer_id`, `number`, `brand_name`, `pdname`, `frey_no`, 
    `order_type_id`, `create_date`
);
```

## 三、匹配算法设计（v5.0）

### 3.1 算法流程

```
┌─────────────────────────────────────────────────────────────────────┐
│                     退货订单匹配算法流程（v5.0）                      │
├─────────────────────────────────────────────────────────────────────┤
│  Step 1: 新增未匹配的退货订单到关联表（type=50）                      │
│          INSERT INTO stock_safe_refund_ref (...)                    │
│          SELECT ... FROM sales_order_history WHERE order_type_id=2  │
│          AND orders_items_id NOT IN (...)                           │
│          ORDER BY create_date ASC LIMIT batch_size                  │
├─────────────────────────────────────────────────────────────────────┤
│  Step 2: 按时间顺序处理退货订单，匹配对应的常规订单（一对多）           │
│                                                                     │
│  For each type=50的退货订单（按refund_create_date ASC排序）：        │
│    ├─ 初始化剩余退货数量：remaining_refund_qty = refund_quantity     │
│    ├─ 初始化匹配次数：match_count = 0                                │
│    ├─ **执行一次查询**，获取符合条件的常规订单列表（0-10条）：         │
│    │   SELECT orders_items_id, total_price, quantity                │
│    │   FROM sales_order_history                                     │
│    │   WHERE order_type_id = 1                                      │
│    │     AND customer_id = {refund.customer_id}                     │
│    │     AND number = {refund.number}                               │
│    │     AND brand_name = {refund.brand_name}                       │
│    │     AND pdname = {refund.pdname}                               │
│    │     AND frey_no = {refund.frey_no}                             │
│    │     AND create_date < {refund.create_date}                     │
│    │     AND orders_items_id NOT IN (已完全使用的常规订单ID)          │
│    │   ORDER BY create_date DESC LIMIT 10                           │
│    │                                                               │
│    ├─ **遍历返回的常规订单列表**，直到退货数量用完或遍历完：            │
│    │   ├─ 匹配成功（找到常规订单）：                                  │
│    │   │   match_count += 1                                         │
│    │   │   processed_quantity = normal_quantity + remaining_refund_qty│
│    │   │                                                           │
│    │   │   判断匹配类型：                                            │
│    │   │   ① match_count == 1（一对一）：                           │
│    │   │      - processed_quantity = 0 → type=11                    │
│    │   │      - processed_quantity > 0 → type=21                    │
│    │   │      - processed_quantity < 0 → type=31                    │
│    │   │                                                           │
│    │   │   ② match_count > 1（一对多）：                             │
│    │   │      - processed_quantity = 0 → type=13                    │
│    │   │      - processed_quantity > 0 → type=23                    │
│    │   │      - processed_quantity < 0 → type=33                    │
│    │   │                                                           │
│    │   │   插入关联表记录（每条匹配创建一条新记录）                    │
│    │   │   更新remaining_refund_qty = processed_quantity            │
│    │   │   若 processed_quantity <= 0：继续遍历下一条常规订单         │
│    │   │   若 processed_quantity > 0：跳出遍历，匹配结束             │
│    │   │                                                           │
│    │   └─ 匹配失败（无返回的常规订单）：                               │
│    │       └─ type=40（未匹配）                                     │
│    └─ 更新退货订单的最终状态                                         │
├─────────────────────────────────────────────────────────────────────┤
│  Step 3: 处理type=21/22/23的常规订单（剩余数量匹配退货订单）           │
│                                                                     │
│  For each type IN (21, 22, 23)的记录（常规订单有剩余）：             │
│    ├─ 获取该常规订单已匹配的退货订单总数                             │
│    ├─ 查找数量未完全抵消的退货订单（type=31/32/33），匹配条件相同      │
│    ├─ 匹配成功：                                                     │
│    │   ├─ 更新匹配次数：match_count += 1                            │
│    │   ├─ 重新计算processed_quantity                                │
│    │   ├─ 若 processed_quantity = 0 → type=12（常规订单被多条退货订单分摊完）│
│    │   ├─ 若 processed_quantity > 0 → type=22（常规订单仍有剩余）    │
│    │   └─ 更新关联表                                                │
│    └─ 匹配失败：保持原type不变                                       │
└─────────────────────────────────────────────────────────────────────┘
```

### 3.2 数量分摊逻辑说明

**场景示例：**

**场景1：一条退货订单匹配多条常规订单后完全抵消（type=13）**
- 退货订单：quantity=-6（退6件）
- 常规订单1：quantity=3（3件）
- 常规订单2：quantity=3（3件）

匹配过程：
1. 匹配常规订单1：processed_quantity = 3 + (-6) = -3，match_count=1 → type=31
2. 继续匹配常规订单2：processed_quantity = 3 + (-3) = 0，match_count=2 → type=13

**场景2：一条常规订单被多条退货订单分摊完（type=12）**
- 常规订单：quantity=5（5件）
- 退货订单1：quantity=-2（先退2件）
- 退货订单2：quantity=-3（后退3件）

匹配过程：
1. 退货订单1匹配常规订单：processed_quantity = 5 + (-2) = 3，match_count=1 → type=21
2. 退货订单2匹配常规订单：processed_quantity = 3 + (-3) = 0，match_count=2 → type=12

**场景3：一条退货订单匹配多条常规订单后常规订单仍有剩余（type=23）**
- 退货订单：quantity=-5（退5件）
- 常规订单1：quantity=3（3件）
- 常规订单2：quantity=3（3件）

匹配过程：
1. 匹配常规订单1：processed_quantity = 3 + (-5) = -2，match_count=1 → type=31
2. 继续匹配常规订单2：processed_quantity = 3 + (-2) = 1，match_count=2 → type=23

**场景4：一条常规订单被多条退货订单分摊后仍有剩余（type=22）**
- 常规订单：quantity=10（10件）
- 退货订单1：quantity=-3（退3件）
- 退货订单2：quantity=-2（退2件）

匹配过程：
1. 退货订单1匹配常规订单：processed_quantity = 10 + (-3) = 7，match_count=1 → type=21
2. 退货订单2匹配常规订单：processed_quantity = 7 + (-2) = 5，match_count=2 → type=22

### 3.3 批量处理SQL

**Step 1: 新增未匹配的退货订单到关联表（type=50）**

```sql
INSERT INTO stock_safe_refund_ref (
    refund_order_items_id,
    oe,
    brand_name,
    product_name,
    barcode,
    customer_id,
    product_price,
    refund_total_price,
    refund_quantity,
    refund_create_date,
    match_count,
    type
)
SELECT 
    orders_items_id,
    number AS oe,
    brand_name,
    pdname AS product_name,
    frey_no AS barcode,
    customer_id,
    price AS product_price,
    total_price AS refund_total_price,
    quantity AS refund_quantity,
    create_date AS refund_create_date,
    0 AS match_count,
    50 AS type
FROM sales_order_history
WHERE order_type_id = 2
  AND orders_items_id NOT IN (
      SELECT refund_order_items_id FROM stock_safe_refund_ref
  )
ORDER BY create_date ASC
LIMIT 1000;
```

**Step 2: 为type=50的退货订单匹配常规订单**

```sql
-- 获取待匹配的退货订单（按时间顺序）
SELECT 
    refund_order_items_id, customer_id, oe, brand_name,
    product_name, barcode, refund_total_price, refund_quantity,
    refund_create_date, match_count
FROM stock_safe_refund_ref
WHERE type = 50
ORDER BY refund_create_date ASC
LIMIT 100;

-- 查找匹配的常规订单（一次返回0-10条）
SELECT orders_items_id, total_price, quantity
FROM sales_order_history
WHERE order_type_id = 1
  AND customer_id = :customer_id
  AND number = :oe
  AND brand_name = :brand_name
  AND pdname = :product_name
  AND frey_no = :barcode
  AND create_date < :refund_create_date
  AND orders_items_id NOT IN (
      SELECT normal_order_items_id FROM stock_safe_refund_ref
      WHERE type IN (11, 12)
  )
ORDER BY create_date DESC
LIMIT 10;

-- 插入新的匹配记录（每条匹配创建一条新记录）
INSERT INTO stock_safe_refund_ref (...) VALUES (...);

-- 更新匹配失败的记录为type=40
UPDATE stock_safe_refund_ref SET type = 40
WHERE refund_order_items_id = :refund_order_items_id AND type = 50;
```

**Step 3: 处理type=21/22/23的常规订单（剩余数量匹配退货订单）**

```sql
-- 获取常规订单有剩余的记录
SELECT ... FROM stock_safe_refund_ref WHERE type IN (21, 22, 23);

-- 查找数量未完全抵消的退货订单（type=31/32/33）
SELECT ... FROM stock_safe_refund_ref 
WHERE type IN (31, 32, 33)
  AND customer_id = :customer_id AND oe = :oe 
  AND brand_name = :brand_name AND product_name = :product_name 
  AND barcode = :barcode
ORDER BY refund_create_date ASC LIMIT 1;
```

## 四、优化策略

### 4.1 索引优化

```sql
ALTER TABLE `sales_order_history` ADD INDEX `idx_match_refund` (
    `customer_id`, `number`, `brand_name`, `pdname`, `frey_no`, 
    `order_type_id`, `create_date`
);

ALTER TABLE `sales_order_history` ADD INDEX `idx_order_type_date` (`order_type_id`, `create_date`);
```

### 4.2 分批处理策略

| 场景 | 批次大小 | 执行频率 |
|------|---------|---------|
| 首次全量同步 | 100条/批 | 一次性执行 |
| 增量同步 | 500条/批 | 每天或每小时 |

### 4.3 缓存策略

使用Redis缓存已完全使用的常规订单ID：
- 缓存键：`stock_safe:fully_used_normal_ids`
- 存储类型：Set
- 过期策略：同步完成后清空
