# 05 设计说明与风险

## 5.1 设计说明与考虑因素

1. **职责分离**：销量表专注净销量采集与聚合（日/月/年净销量、标准差、月度JSON），安全库存表专注计算与展示（阈值、状态）。避免数据采集任务与库存计算任务耦合，两者可独立调度。

2. **净销量逻辑**：销量表的销量字段均为**净销量**（扣除退货）。无退货订单取 `sales_order_history.quantity`；部分退货订单（type=21/22）取 `stock_safe_refund_ref.processed_quantity`（退货后剩余）；完全退货订单（type=11/12/13）净销量为0。详见[销量计算逻辑](01_设计概述与销量计算.md#14-销量数据来源与计算逻辑)。

3. **移除 `stat_date`**：销量表数据时效由 `updated_at` 体现（每次采集刷新即更新）；安全库存表为计算快照，通过定时任务整体刷新，逐条统计日期无业务意义。

4. **`(oe, brand_name)` 联合唯一键**：同一 OE 号存在多个品牌，需 (oe, brand_name) 共同唯一。两表唯一键均为 `uk_oe_brand`，关联关系基于此键。`brand_name` 在两表中均为 NOT NULL。

5. **`abc_classification` 归属**：放在安全库存表。ABC 分类属库存管控参数（直接决定 Z系数与覆盖天数），非销量属性。test.md 中 ABC 分类与安全库存参数强绑定。

6. **预计算 vs 实时计算**：推荐 **预计算存储**。前端直接读取结果，计算逻辑在定时任务/服务层完成，降低查询时计算开销。代价是库存状态存在刷新延迟（见潜在风险）。

7. **冗余字段**：`brand_name`/`product_name`/`barcode` 在安全库存表冗余，避免前端展示时跨表 JOIN。需在同步任务中以销量表为准刷新，保持一致。

8. **配置参数不落表**：Z系数、覆盖天数、补货周期、预警天数、积压阈值建议作为 **全局配置**（配置表或常量），不放入安全库存表逐行存储。原因：这些参数按 ABC 分类统一设定（见 test.md 速查表），逐行存储会产生大量冗余且更新易不一致。

9. **除零保护**：`avg_daily_sales = 0` 时计算可卖天数会出现除零，需在计算逻辑中特殊处理（如可卖天数置为 0 或 NULL，状态按业务判定为"正常"或"库存积压"）。

10. **季节系数范围限制**：test.md 规定季节系数范围 0.7~1.3，计算结果超出范围需截断（小于 0.7 取 0.7，大于 1.3 取 1.3）。

## 5.2 潜在风险

| 风险 | 影响 | 应对建议 |
|------|------|---------|
| `available_stock` 数据来源不明 | 库存状态无法准确判定 | 待确认数据来源（WMS/库存系统），明确同步频率与方式 |
| type=23 净销量少计 | type=23（部分退货-退货订单视角）的 processed_quantity>0 表示常规订单有剩余，当前逻辑忽略会导致该部分销量计为0 | 待确认是否可接受；若不可接受需补充 type=23 最新记录的 processed_quantity |
| 数据冗余不一致 | 两表 `brand_name` 等字段脱节 | 同步任务以销量表为准刷新安全库存表冗余字段 |
| 预计算时效性 | 库存状态滞后于实际库存 | 明确刷新频率；`available_stock` 变化时触发状态重算 |
| 季节系数按月变化 | 安全库存值需周期性刷新 | 定时任务每月初重算 `season_coefficient` |
| 大批量 OE 重算性能 | 定时任务耗时长 | 分批处理；仅重算有销量变动的 (oe, brand_name) |
| 新 (oe, brand_name) 同步缺口 | 销量表新增组合未同步至安全库存表 | 同步任务以销量表 (oe, brand_name) 为基准 upsert 安全库存表 |
| 除零异常 | `avg_daily_sales=0` 时可卖天数计算报错 | 计算逻辑增加除零保护，置 0 或 NULL |
| 销量计算依赖退货匹配完成度 | stock_safe_refund_ref 未跑完时净销量不准 | 销量计算任务需在退货匹配任务（step1/2/3）完成后执行 |
