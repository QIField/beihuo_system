# 安全库存同步 CRM 方案设计

## 一、背景与问题

当前 `push_data.py` 直接从 `stock_safe` 表查询需补货记录，全量推送到 CRM，存在以下问题：

1. **无同步管控表**：无法记录哪些商品需要同步、上次同步时间。
2. **前端无法干预**：业务人员无法选择要同步的商品、无法手动触发同步。
3. **推送时机不可控**：推送值完全取自 `stock_safe` 计算结果，推送时机不由业务掌控。

## 二、表结构

表名：`stock_safe_sync_queue`（安全库存同步队列表）

| 字段          | 类型                              | 说明                          |
| ----------- | ------------------------------- | --------------------------- |
| id          | BIGINT UNSIGNED AUTO\_INCREMENT | 主键                          |
| number      | VARCHAR(255) NOT NULL           | OE 号（CRM 匹配键）               |
| brand\_name | VARCHAR(255) NOT NULL           | 品牌名（CRM 匹配键）                |
| frey\_no    | VARCHAR(255)                    | 条码（取自 stock\_safe 第一条，仅供参考） |
| pdname      | VARCHAR(255)                    | 产品名称（冗余展示）                  |
| synced\_at  | DATETIME                        | 最后一次成功同步时间；NULL 表示待同步       |
| created\_at | DATETIME                        | 创建时间                        |
| updated\_at | DATETIME                        | 更新时间                        |

约束：

- 唯一键 `(number, brand_name)`
- 索引 `synced_at`

## 三、核心逻辑

### 3.1 状态判定

- `synced_at IS NULL` → 待同步（从未同步 / 同步失败待重试 / 值变化需重同步）
- `synced_at IS NOT NULL` → 已同步（最后一次同步成功）

同步失败时 `synced_at` 保持 NULL，下次任务自动重试，不限制重试次数。失败详情仅写日志。

### 3.2 推送值来源

队列不存储推送参数，同步执行时**实时从** **`stock_safe`** **表读取**：

- `safety_stock` ← stock\_safe.safety\_stock
- `max_stock` ← stock\_safe.stock\_upper\_limit
- `season_coefficient` ← stock\_safe.season\_coefficient
- `warehouse_id` = 1，`isnotstock` = '0'

按 `(number, brand_name)` 取 stock\_safe 中第一条记录的值。

### 3.3 自动入队逻辑（定时任务执行）

`stock_safe` 刷新完成后，扫描符合补货条件的记录（复用 `replenish_dao.fetch_replenish_data` 筛选条件），按 `(number, brand_name)` 去重后写入队列：

| 队列中已有记录的 synced\_at | 处理方式                                   |
| ------------------- | -------------------------------------- |
| 不存在                 | 新增一行，synced\_at = NULL                 |
| NULL（待同步）           | 保持 NULL                                |
| 有值（已同步）             | 重置为 NULL（stock\_safe 每日刷新，值可能变化，需重新同步） |

已不在补货范围内的队列记录不自动删除，由前端手动移除。

### 3.4 同步执行逻辑

- 扫描 `synced_at IS NULL` 的记录，按 `created_at` 升序分批处理（每批 50 条，复用同一 `CrmGzbbrSpider` 实例）。
- 每条记录：
  1. 从 `stock_safe` 取推送值（见 3.2）。
  2. 调用 CRM `Product.Product/list` 按 OE 号匹配 `product_id`（每次实时匹配，不缓存）。
  3. 调用 CRM `Product.Product/saveSafeStock` 推送。
  4. 成功 → 更新 `synced_at = NOW()`；失败 → 保持 NULL，详情记录日志。

## 四、流程

### 4.1 定时任务流程（每日 03:00）

```
Step1 爬取销售订单
Step2 刷新 stock_safe
Step3 生成补货 Excel
Step4 同步队列管理 + 推送
  ├─ 4a 自动入队：扫描 stock_safe 补货候选 → upsert 到 sync_queue
  └─ 4b 执行同步：扫描 synced_at IS NULL 的记录 → 推送 CRM → 回写 synced_at
```

### 4.2 前端操作流程

```
补货候选列表（stock_safe 需补货记录）
      │ 选择商品
      ▼
  加入同步队列（sync_queue，synced_at = NULL）
      │
      ▼
  同步队列表
      ├─ 立即同步 → 推送 CRM → 成功则 synced_at 有值
      ├─ 重同步   → synced_at 重置为 NULL
      └─ 删除     → 从队列移除
```

前端页面为双 Tab 结构：

- **补货候选 Tab**：展示 stock\_safe 中需补货且未入队的记录，支持多选"加入同步队列"。
- **同步队列 Tab**：展示队列记录，同步状态由 `synced_at` 派生（NULL=待同步，有值=已同步），支持立即同步、重同步、删除。
