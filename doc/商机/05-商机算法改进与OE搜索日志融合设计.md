# 商机算法改进与 OE 搜索日志融合设计

## 一、文档目标

本设计文档聚焦两个核心命题：

1. **OE 搜索日志（`oe_search_log`）目前仅完成采集入库，尚未参与商机计算**，如何把它转化为有效的商机信号；
2. **当前商机评分与补货算法偏经验化、维度单一**，如何从算法层面进行改进，使其更准确、可解释、可运营。

本文只讨论**设计、算法与数据流**，不产出代码。后续开发可基于本文拆分为具体任务。

## 二、当前现状复盘

### 2.1 数据流

当前商机计算链路如下：

```
wechat_daily_quote_detail ──► niche_opportunity
        │                            │
        │                            ▼
        │                     crmapp_beihuo
        │                     (可用库存 / 在途数量)
        ▼
   STR_TO_DATE(create_date)
```

`oe_search_log` 的数据流是独立的：

```
CRM /api/Product.Product/oeSearchLog
        │
        ▼
crawl_oe_search_log_by_page
        │
        ▼
clean_oe_search_log
        │
        ▼

        │
        ▼

```

**结论：`oe_search_log` 与商机计算没有任何数据交互，属于“沉睡资产”。**

### 2.2 当前算法

评分体系（满分 100）：

| 维度 | 权重 | 计算方式 |
|------|------|----------|
| 询价热度 | 40% | `min(100, inquiry_count_30d / P80_inquiry * 100)` |
| 缺货强度 | 30% | `out_of_stock_rate_30d * 100` |
| 客户广度 | 20% | `min(100, customer_count_30d / P80_customer * 100)` |
| 需求趋势 | 10% | 环比上涨加分，下降/持平为 0 |

补货建议：

```
日均询价数 = inquiry_count_30d / 30
建议备货量 = 日均询价数 × 0.3 × 15
建议补货量 = max(0, 建议备货量 - 可用库存 - 在途数量)
```

触发条件（满足任一）：

1. `opportunity_score >= 60` 且 `available_stock < suggested_stock_qty * 0.5`
2. `out_of_stock_rate_30d >= 0.5` 且 `inquiry_count_30d >= 3`

| 编号 | 问题 | 影响 | 优先级 |
|------|------|------|--------|

## 三、OE 搜索日志融合设计

### 3.1 OE 搜索日志能补充什么

`oe_search_log` 记录的是 CRM 中**用户主动搜索 OE 码**的行为，位于询价之前（或并行）。它至少能提供：

- **搜索热度**：某 OE 码近 30 天被搜索多少次；
- **搜索客户广度**：有多少不同客户/公司在搜；
- **搜索-询价转化缺口**：搜了但没询价，可能意味着“我们没有报价/没有库存/价格不优”；
- **需求确认**：搜索与询价同时高，说明需求真实且旺盛。

### 3.2 新增指标定义

在商机计算中新增以下 OE 搜索维度指标（建议命名为 `search_*`）：

| 指标 | 字段名 | 口径 |
|------|--------|------|
| 近 30 天 OE 搜索次数 | `search_count_30d` | `oe_search_log` 中 `search_date` 落在近 30 天，且 `oe_number` 匹配的记录数 |
| 近 30 天搜索客户去重数 | `search_customer_count_30d` | 上述范围内 `company_id` / `user_id` 去重数 |
| 上一个 30 天 OE 搜索次数 | `search_count_prev_30d` | 用于趋势对比 |

> 口径说明：OE 搜索日志中 `oe_number` 可能与 `wechat_daily_quote_detail.oe_code` 存在大小写、空格差异，计算时统一 `TRIM()` + `LOWER()` 或保持现有 `utf8mb4_unicode_ci` 规则后匹配。
>
> **注**：`search_to_inquiry_rate`（搜索-询价转化率）和 `search_gap_score`（搜索-缺货缺口分）已下线。OE 搜索行为主要由业务员发起，不能直接等同于客户需求，因此不再用于衡量需求缺口或转化漏斗。

### 3.3 融合后的数据流

```
wechat_daily_quote_detail ──┐
                            ├──► 数据清洗/对齐 ──► 商机计算 ──► niche_opportunity
oe_search_log ──────────────┘              │
                                           ▼
                                    crmapp_beihuo
```

计算层在一次任务中同时读取两张表，按 `oe_code` 对齐后统一打分。

## 四、评分模型改进

### 4.1 总体思路

引入 OE 搜索维度后，评分模型从 4 维度扩展为 5 维度，并做以下关键调整：

1. **趋势分改为“奖惩对称”**，避免只涨分不掉分；
2. **缺货强度分引入置信度**，小样本时降权；
3. **新增搜索热度分与搜索-询价转化分**，识别“搜得多但还没询过来”的潜在商机；
4. **权重可配置化**，支持按品类/品牌差异化（第一阶段先全局可配，第二阶段支持品类级）。

### 4.2 推荐新评分体系（全局版）

| 维度 | 权重 | 字段 | 含义 |
|------|------|------|------|
| 询价热度 | 30% | `inquiry_score` | 已发生的真实询价热度 |
| 搜索热度 | 15% | `search_score` | 上游搜索热度 |
| 缺货强度 | 25% | `out_of_stock_score` | 问了但缺货，供给缺口 |
| 客户广度 | 15% | `customer_score` | 客户分散度 |
| 需求趋势 | 15% | `trend_score` | 搜索+询价的综合环比趋势 |

**综合评分公式：**

```
opportunity_score =
    0.30 * inquiry_score
  + 0.15 * search_score
  + 0.25 * out_of_stock_score
  + 0.15 * customer_score
  + 0.15 * trend_score
```

> 注：权重为推荐默认值，应迁移到配置中心/数据库配置表，便于运营调参。

### 4.3 各维度新算法

#### 4.3.1 询价热度分（不变但权重下调）

```
inquiry_score = min(100, inquiry_count_30d / P80_inquiry * 100)
```

#### 4.3.2 搜索热度分

```
search_score = min(100, search_count_30d / P80_search * 100)
```

`P80_search`：全部 OE 码近 30 天搜索次数的第 80 百分位。

#### 4.3.3 缺货强度分（引入置信度）

原算法：

```
oos_score = out_of_stock_rate_30d * 100
```

问题：当 `inquiry_count_30d = 1` 且缺货 1 次时，得 100 分，噪声极大。

改进后：

```
confidence = min(1.0, inquiry_count_30d / 10)   # 样本量越大置信度越高，10 次达到满信
base_oos_score = out_of_stock_rate_30d * 100
oos_score = base_oos_score * (0.3 + 0.7 * confidence)
```

解释：

- 询价 0 次：缺货分为 0；
- 询价 1 次且全缺货：`100 * (0.3 + 0.7 * 0.1) = 37` 分；
- 询价 10 次及以上且全缺货：100 分。

这样小样本高缺货率不会被过度放大。

#### 4.3.4 客户广度分（不变）

```
customer_score = min(100, customer_count_30d / P80_customer * 100)
```

后续可考虑：若同一客户反复询价（如超过 5 次），超过部分降权，避免单个客户刷屏。

#### 4.3.5 需求趋势分（奖惩对称）

原算法只奖励增长，不惩罚下降。改进后综合搜索与询价的变化：

```
# 综合需求指数 = 询价次数 + α * 搜索次数
# α 为搜索→询价的经验折算系数，默认 0.3
current_index = inquiry_count_30d + 0.3 * search_count_30d
prev_index = inquiry_count_prev_30d + 0.3 * search_count_prev_30d

if prev_index == 0:
    trend_rate = 1.0 if current_index > 0 else 0.0
else:
    trend_rate = (current_index - prev_index) / prev_index

# 趋势分：-50% → 0 分，持平 → 50 分，+50% → 100 分
trend_score = max(0, min(100, 50 + trend_rate * 100))
```

相比原算法，改进点：

- 下降会扣分；
- 引入搜索数据，趋势判断更全面；
- 持平给 50 分而非 0 分，避免大量稳定需求品被埋没。

### 4.4 商机等级划分（不变）

| 等级 | 分数区间 | 含义 |
|------|----------|------|
| S | ≥ 80 | 极高价值商机 |
| A | 60 ~ 79 | 高价值商机 |
| B | 40 ~ 59 | 中等商机 |
| C | 20 ~ 39 | 低价值商机 |
| D | < 20 | 无明显商机 |

## 五、补货建议算法改进

### 5.1 当前算法的问题

1. 固定转化系数 `0.3`：不同品类、不同 OE 码的真实转化率差异大；
2. 固定备货天数 `15`：未考虑供应商交期、周转速度；
3. 触发条件二（高缺货率低询价）与触发条件一（高评分低库存）可能产生冲突或重复推荐；
4. 未使用安全库存模块结果，也未考虑 MOQ、包装规格。

### 5.2 改进方向

#### 5.2.1 动态转化系数

不再使用全局固定 `0.3`，而是按**品类/品牌级别**计算历史转化率：

```
category_conversion_rate =
    历史该品类成交数量 / 历史该品类询价次数
```

若品类数据不足，fallback 到全局默认值 `0.3`。

更优方案（需销售历史数据）：按 OE 码级别计算近 90 天转化率，但有冷启动问题，建议：

```
conversion_rate(oe) =
    0.6 * category_conversion_rate + 0.4 * global_conversion_rate
```

未来若 `sales_order_history` 数据可用，可替换为：

```
conversion_rate(oe) =
    0.5 * oe_sales / oe_inquiry
  + 0.3 * category_conversion_rate
  + 0.2 * global_conversion_rate
```

#### 5.2.2 动态备货天数

备货天数不再固定为 15，改为按**供应商交期 + 补货周期 + 安全缓冲**估算：

```
lead_time_days = 品类默认交期（可配置，默认 7 天）
review_period_days = 补货评审周期（可配置，默认 7 天）
safety_buffer_days = 安全缓冲（可配置，默认 3 天）
stock_days = lead_time_days + review_period_days + safety_buffer_days
```

若未来接入安全库存模块，可直接使用 `stock_safe` 表中的建议备货天数或安全库存量。

#### 5.2.3 需求预测（简单加权移动平均）

用近 30 天日均询价作为预测基准过于粗糙，可改为近 7/30/60 天加权：

```
# 输入：近 7 天、近 30 天、近 60 天询价次数
forecast_daily_demand =
    0.5 * (inquiry_count_7d / 7)
  + 0.3 * (inquiry_count_30d / 30)
  + 0.2 * (inquiry_count_60d / 60)
```

> 当前聚合 SQL 只输出 30 天和上一个 30 天，若要实现该公式需扩展聚合口径。

#### 5.2.4 建议备货量新公式

```
forecast_daily_demand = 加权移动平均日均需求
suggested_stock_qty = forecast_daily_demand × conversion_rate × stock_days
```

#### 5.2.5 触发条件合并与简化

原两个触发条件逻辑有重叠，建议合并为单一规则：

```
# 推荐补货当且仅当：
# 1. 商机评分 >= 50 或 缺货率 >= 50%（二者至少满足其一）
# 2. 当前可用库存 + 在途 < 建议备货量 × 0.5（库存不足）
# 3. 近 30 天询价次数 >= 3（避免小样本）

should_replenish =
    (opportunity_score >= 50 or out_of_stock_rate_30d >= 0.5)
    and (available_stock + transit_quantity) < suggested_stock_qty * 0.5
    and inquiry_count_30d >= 3

replenish_suggestion = max(0, ceil(suggested_stock_qty - available_stock - transit_quantity)) if should_replenish else 0
```

相比原算法：

- 不再让“高评分低库存”和“高缺货率低询价”两条独立触发，避免冲突；
- 统一以“商机价值高 + 库存不足”为核心逻辑；
- 保留最小询价次数门槛，过滤噪声。

#### 5.2.6 MOQ 与包装规格（未来扩展）

若后续接入商品主数据，可加入：

```
replenish_suggestion = ceil_to_moq(suggested_stock_qty - available_stock - transit_quantity, moq_qty)
```

第一阶段可先不做，但在表结构中为 `moq`、`packing_spec` 预留字段或仅在导出时做向上取整。

## 六、数据质量改进

### 6.1 清洗规则

在商机计算前增加统一清洗层：

| 规则 | 处理方式 |
|------|----------|
| 无效 OE 码 | 过滤 `NULL`、`''`、`'0'`、纯空格 |
| 重复询价 | 同一 `oe_code` + 同一 `inquiry_customer` 在 24h 内多次出现，只计 1 次 |
| 测试/内部客户 | 维护黑名单（如 `测试`、`test`、`内部员工` 等关键词），过滤或降权 |
| 异常搜索 | `oe_search_log` 中同一 `user_id` 在 1 分钟内搜索同一 OE 码超过 10 次，视为刷屏，只计 1 次 |
| 离群值处理 | 单日询价次数超过该 OE 历史均值 5 倍，标记为异常，可剔除或单独展示 |

### 6.2 P80 基准的稳定性

当前 P80 每天根据当日全部 OE 码重新计算，导致历史评分不可比。建议：

- 将 P80 基准值每天持久化到配置表 `niche_config`；
- 初始值用全量历史数据计算，后续可按周更新，避免每日抖动；
- 或采用**滚动 30 天窗口**计算 P80，使基准更稳定。

## 八、工程化改进

### 8.1 刷新机制

当前：先 `TRUNCATE` 再 `INSERT`，计算期间列表页无数据。

改进方案（二选一，推荐方案 B）：

- **方案 A：按日期删除 + 插入**
  ```sql
  DELETE FROM niche_opportunity WHERE stat_date = :stat_date;
  INSERT INTO niche_opportunity ...
  ```
  优点：保留历史日期数据；缺点：大表 DELETE 可能慢。

- **方案 B：临时表切换**
  1. 写入临时表 `niche_opportunity_tmp`；
  2. 校验行数、抽样对比；
  3. `RENAME TABLE niche_opportunity TO niche_opportunity_old, niche_opportunity_tmp TO niche_opportunity;`
  4. 删除旧表。
  优点：切换瞬间完成，查询端几乎无感知；缺点：需要多一个表。

### 8.2 配置化

将 `WEIGHTS`、`LEVEL_THRESHOLDS`、`INQUIRY_CONVERSION_RATE`、`STOCK_DAYS` 等全部迁移到 `niche_config` 表，启动时读取并缓存，支持热更新。

### 8.3 ~~去重 Excel 导出入口~~

`create_excel.py` 与 `opportunity_replenish_service.generate_replenish_excel()` 已随前端“导出补货清单”按钮一并下线，商机模块不再提供补货清单 Excel 导出功能。

### 8.4 计算任务可观测性

在 `opportunity_compute_service.run_compute` 中增加阶段埋点：

- 每阶段耗时；
- 清洗过滤掉的记录数；
- P80 基准值；
- 各等级商机数量；
- 异常 OE 码列表（如缺货率异常高但询价数极少）。

## 十、关键公式速查

### 10.1 新综合商机评分

```
opportunity_score =
    0.30 * inquiry_score
  + 0.15 * search_score
  + 0.25 * out_of_stock_score
  + 0.15 * customer_score
  + 0.15 * trend_score
```

### 10.2 各维度分数

```
inquiry_score = min(100, inquiry_count_30d / P80_inquiry * 100)
search_score  = min(100, search_count_30d / P80_search * 100)
customer_score = min(100, customer_count_30d / P80_customer * 100)

confidence = min(1.0, inquiry_count_30d / 10)
oos_score = out_of_stock_rate_30d * 100 * (0.3 + 0.7 * confidence)

current_index = inquiry_count_30d + 0.3 * search_count_30d
prev_index = inquiry_count_prev_30d + 0.3 * search_count_prev_30d
trend_rate = (current_index - prev_index) / max(prev_index, 1)
trend_score = max(0, min(100, 50 + trend_rate * 100))
```

### 10.3 新补货建议

```
forecast_daily_demand =
    0.5 * (inquiry_count_7d / 7)
  + 0.3 * (inquiry_count_30d / 30)
  + 0.2 * (inquiry_count_60d / 60)

suggested_stock_qty =
    forecast_daily_demand * conversion_rate * stock_days

should_replenish =
    (opportunity_score >= 50 or out_of_stock_rate_30d >= 0.5)
    and (available_stock + transit_quantity) < suggested_stock_qty * 0.5
    and inquiry_count_30d >= 3

replenish_suggestion =
    max(0, ceil(suggested_stock_qty - available_stock - transit_quantity)) if should_replenish else 0
```
