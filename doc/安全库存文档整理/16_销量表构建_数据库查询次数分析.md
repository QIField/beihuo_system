# 销量表构建流程 - 数据库查询次数分析

> 统计 `run_sync()` 完整执行过程中，应用层到数据库的所有查询往返次数。

## 一、正常成功路径查询明细

| # | 步骤 | 函数 | SELECT | 写操作 |
|---|------|------|--------|--------|
| 1 | DB 聚合抽取 | `fetch_aggregated_sales` | 1 | 0 |
| 2 | 派生计算 | `_derive_fields`(pandas) | 0 | 0 |
| 3 | 清空原表 | `truncate_table` | 0 | 1 DDL |
| 4 | 批量写入 | `batch_insert` | 0 | ⌈N/2000⌉ INSERT |

## 二、查询次数汇总

| 类型 | 次数 | 明细 |
|------|------|------|
| SELECT | 1 | 步骤1 |
| 写操作 | 1 + ⌈N/2000⌉ | 步骤3(×1) + 步骤4(×⌈N/2000⌉) |
| **总 DB 往返** | **2 + ⌈N/2000⌉** | — |

举例：
- N=5000 SKU → 2 + 3 = **5 次**
- N=20000 SKU → 2 + 10 = **12 次**

## 三、涉及的数据库表

| 表名 | 用途 | 访问类型 |
|------|------|---------|
| `sales_order_history` | 销量明细源（第一部分） | SELECT |
| `stock_safe_refund_ref` | 退货关联源（第二部分 + NOT EXISTS） | SELECT |
| `oe_parts_sales` | 目标表（清空/写入） | DDL + INSERT |

## 四、结论

销量表构建流程的 DB 往返次数主要受聚合后 SKU 数 N 影响。聚合查询本身仅1次往返（DB端完成全部 UNION ALL + GROUP BY + SUM CASE），是查询次数控制的核心优化点。
