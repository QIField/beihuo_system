# 退货匹配流程（Step1/2/3）

> 以程序实现为准（`app/services/stock_safe_service/stock_safe_refund_ref_service.py`）。
> 数据来源：`sales_order_history` 表（常规订单 order_type_id=1，退货订单 order_type_id=2）。
> 续篇：Step3 详情与数量分摊场景示例见 [07_退货匹配流程_Step3与示例](07_退货匹配流程_Step3与示例.md)

## 一、整体流程

```
Step1: 新增未匹配退货订单（type=50）
   ↓
Step2: 退货订单 → 匹配常规订单（一对多-退货视角）
   ↓  未匹配 → type=40
Step3: 常规订单剩余 → 匹配 type=40 退货订单（一对多-常规视角）
   ↓  仍未匹配 → type=41
```

## 二、Step1：新增未匹配退货订单

- 从 `sales_order_history` 取 `order_type_id=2` 且未在关联表中的退货订单
- 插入关联表，标记 `type=50`（未进行匹配）
- 循环批量插入（默认 1000 条/批），直到无新数据

## 三、Step2：退货订单匹配常规订单

### 3.1 处理逻辑

1. 批量获取 `type=50` 退货订单，按 `refund_create_date` 升序
2. 对每条退货订单查询匹配的常规订单（0-10 条）
3. 排序后遍历常规订单，分摊退货数量直到用完或遍历完
4. 匹配成功的批量插入；未匹配的更新为 `type=40`

### 3.2 匹配条件（find_matching_normal_orders）

- `order_type_id = 1`（常规订单）
- 客户匹配（二选一）：`customer_id = :customer_id OR fullname = :customer_name`
- `number = :number`、`brand_name`、`pdname = :pdname`、`frey_no = :frey_no` 完全匹配
- `create_date < :refund_create_date`（常规订单在退货订单之前创建）
- 排除已匹配常规订单：`NOT EXISTS` type IN (11,12,13,21,22,23,31,32,33)
- 同批次内通过 `excluded_normal_ids` 内存去重

### 3.3 常规订单排序策略（_sort_normal_orders）

三级降级排序，优先匹配最合理的常规订单：

1. **直接匹配**：存在数量等于 abs(退货数量) 的订单 → 该订单排最前，其余按数量降序
2. **组合匹配**：存在子集和等于 abs(退货数量) 的组合 → 组合成员排前，按数量降序
3. **无匹配**：全部按数量降序（大→小）

### 3.4 数量分摊与 type 计算

- `processed_quantity = 常规订单quantity + 剩余退货数量`
- 第 1 次匹配 mode=1（一对一），后续 mode=3（一对多-退货视角）
- type 由 processed_quantity 正负与 mode 计算（见 [03_退货关联表结构](03_退货关联表结构.md)）
- 退货数量用完（processed_quantity > 0）则跳出遍历

### 3.5 批后处理

- 批量插入匹配记录（`batch_insert_matched_refund`，ON DUPLICATE KEY UPDATE）
- 删除已匹配退货单的 type=50 占位行（`delete_pending_by_refund_ids`）
- 未匹配退货单更新为 type=40（`batch_update_unmatched_to_type40`）
- 统一同 refund 的 type（`update_type_to_by_refund_order`）
