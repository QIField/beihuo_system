### 1.2 cost_price 数据链路与语义

数据由**备货爬虫**维护（[crawl_service.py](file:///e:/Barbori/complete_project/beihuo_system/app/services/procurement_service/crawl_service.py) L255-L262 批量写入含 `cost_price`），爬虫流程为**先清空再全量重插**。

⚠️ 两个必须写进口径的语义限制：

1. **当前成本，非历史成本**：`cost_price` 是爬虫抓取时点的现行成本价。用它乘以历史订单数量算利润，本质是"**按现行成本估算**"口径，前端需标注口径说明（同欠款余额卡的 sub 标注模式）。
2. **爬虫清空重灌窗口**：清空与重插之间存在表数据不完整的瞬间，实时查询可能取不到成本（利润临时偏差）。低频窗口，可接受；方案2 快照表可彻底消除该波动。

## 二、关联路径设计

`sales_order_history`（订单明细）与 `crmapp_compare_summary` 的桥接字段对照：

| 路径 | 关联条件 | 索引支持 | 评估 |
| --- | --- | --- | --- |
| **A：frey_no** | `sales_order_history.frey_no = crmapp_compare_summary.frey_no`（+ `company='fsbbr'`） | `uk_frey_no_company` 唯一索引 | ✅ **推荐**。两侧字段天然对应（菲尔号 ↔ Frey编号），唯一索引点查，且**一 frey_no 一行无去重问题** |
| B：oe | `sales_order_history.number = crmapp_compare_summary.oe` | ❌ `oe` 无索引 | 仅作 A 的**兜底**；若采用需先 `ALTER TABLE crmapp_compare_summary ADD INDEX idx_oe (oe)`（VARCHAR(255) utf8mb4 注意前缀长度限制） |

**推荐策略**：主路径 A（frey_no 匹配）；明细行 `frey_no` 为空或未命中时，是否回退路径 B（oe 匹配）**取决于上线前数据探查结果**（见第七节探查 1/2），探查前不在方案中固化。

## 三、利润口径定义

沿用现有指标卡口径框架（明细 → 订单级聚合基表，见 [visit_stats_dao.py](file:///e:/Barbori/complete_project/beihuo_system/app/dao/visit_dao/visit_stats_dao.py) `_order_amount_subquery`）：

| 指标 | 口径 | 状态 |
| --- | --- | --- |
| 累计利润 | `Σ常规订单明细(total_price − quantity × cost_price)`，仅常规订单（order_type_id=1），退货订单不计入（与"累计拿货额"口径一致）；1:N 绑定按 partner_ids 集合求和 | ⚠️ 退货是否抵减利润待业务确认 |
| 近30天毛利额 | 同上 + 订单级 `create_date` 30 天窗口（与"成交金额"窗口一致） | ⚠️ 同上 |
| 成本匹配失败行 | 明细行匹配不到成本（frey_no/oe 均未命中，或 cost_price 为 0/NULL）时该行利润不可算，处理策略见下 | ⚠️ 待业务确认 |

**成本缺失行处理（三选一，待确认）**：

- A. 剔除该行（利润与销售额均不计）→ 利润低估但稳健；
- B. 仅利润中剔除、销售额照计 → 利润率失真；
- C. 利润照常累计 + 前端 badge 标注"部分成本缺失（N 件）" → 信息最全，实现成本略高。

> `cost_price = 0` 建议视为"未维护"（同缺失处理），与真实零成本业务上不可区分，需业务确认。

### 4.2 查询流程（单条 SQL，JOIN 在订单级基表内完成）

```
订单级基表子查询（扩展 _order_amount_subquery 思路）：
  SELECT orders_id,
         SUM(total_price)                    AS order_amount,
         SUM(quantity * ccs.cost_price)      AS order_cost,
         MAX(customer_id)                    AS customer_id,
         MAX(create_date)                    AS create_date
  FROM sales_order_history soh
  LEFT JOIN crmapp_compare_summary ccs
         ON ccs.frey_no = soh.frey_no COLLATE utf8mb4_unicode_ci
        AND ccs.company = 'fsbbr'
        AND soh.frey_no IS NOT NULL AND soh.frey_no != ''
  WHERE soh.customer_id IN (:partner_ids)
  GROUP BY orders_id;

外层：SUM(CASE order_type_id=1 THEN order_amount - order_cost END)        → 累计利润
      SUM(CASE order_type_id=1 AND create_date>=30d THEN 同上 END)          → 近30天毛利额
      另计"成本缺失件数"（ccs.frey_no IS NULL 或 cost_price<=0 的明细数）    → badge 用
```

成本是明细级属性，JOIN 必须放在基表子查询**内部**（每明细行乘各自成本后聚合到订单级），不能在外层订单级再 JOIN。

### 4.3 性能分析

| 环节 | 评估 |
| --- | --- |
| 驱动侧 sales_order_history | `idx_customer_id` 已有索引，过滤 partner_ids（1:N 通常 1~3 个），单客户明细数百~数千行；现有拿货额/退货指标同路径已验证 |
| 探测侧 crmapp_compare_summary | `uk_frey_no_company` 唯一索引等值探查，每明细行一次索引点查，行数 = 该客户明细数，毫秒级 |
| 读取列 | 仅取聚合所需 5~6 列，不跑 group_concat/状态列，与现有"轻量基表"约定一致 |
| **结论** | 详情页单次请求增量预计 **<100ms**，与现有 7 条统计查询同量级 → **方案1 可行** |

**触发方案2 的阈值（上线后观测）**：详情接口 P95 > 1s，或慢查询日志出现该 SQL，或客户明细行数规模增长导致 IN/JOIN 膨胀（去重 frey_no > 5000 量级）。

## 五、方案2：详情卡快照表定时更新（兜底）

即启用《[02-拓展设计文档.md](02-拓展设计文档.md)》1.3 已设计的 `visit_customer_stats` 快照表（含 `profit_total` / `profit_30d` 字段），本方案只做**裁剪落地**：

- **表**：按 1.3 DDL 落地（字段可先只启用利润相关 + 主键维度列，其余列保留 NULL 由后续指标复用）；唯一键 `uk_stat_partner (stat_date, partner_id)` / `uk_stat_amap (stat_date, amap_customer_id)`。
- **定时任务**：`visit_stats_daily_refresh` 每日 **04:00~05:00**（避开 03:00 销售爬虫与 02:00 欠款窗口），全量重算，流程参考 `oe_parts_sales` 的 备份→写入→校验→替换→清理。
- **读取侧**：stats 接口利润卡改读快照（当日最新 stat_date 行），前端标注"**数据截至 T-1**"。
- **时效补偿**：当日新订单/新绑定客户不在快照内 → 可选"进入详情页时惰性重算该客户当日行"策略（按需决定，先不做）。
- **利润算法复用**：快照重算 SQL 即方案 4.2 的聚合 SQL，仅把触发时机从"每次请求"改为"每日任务"，两方案算法同源，切换成本低。

**方案2 相比方案1 的净收益**：消除实时 JOIN 开销 + 消除爬虫清空重灌窗口的波动 + 为后续列表页指标/趋势图铺路；代价是 T-1 时效与任务运维。

## 六、技术风险与注意事项

1. **Collation**：`crmapp_compare_summary` 关联如报 `Illegal mix of collations`，显式 `COLLATE utf8mb4_unicode_ci`（项目已有先例：[crawl_service.py](file:///e:/Barbori/complete_project/beihuo_system/app/services/procurement_service/crawl_service.py) L481-L483 的 JOIN 均显式 COLLATE）。
2. **frey_no 空值污染**：`sales_order_history.frey_no` 可能为空串，JOIN 条件必须排除空串/NULL，否则会错误匹配 `crmapp_compare_summary` 中 frey_no 为空的行。
3. **非唯一匹配兜底**：`uk_frey_no_company` 保证 (frey_no, company) 唯一，但历史数据可能存在未清理的重复行 → JOIN 后按 frey_no 取 `MAX(cost_price)` 或 `MIN(id)` 去重，探查 SQL 验证（第七节探查 3）。
4. **成本价精度**：`crmapp_compare_summary.cost_price` 为 DECIMAL(10,2)，`sales_order_history.cost_price` 为 DECIMAL(18,4)，两套精度并存（后者本期不使用）；利润聚合建议保留 2 位小数。
5. **`oe` 兜底索引**：若探查结论要求启用路径 B，`ALTER TABLE crmapp_compare_summary ADD INDEX idx_oe (oe)` 需在低峰执行（十万级表，在线 DDL 可接受），并注意 MySQL 5.7 utf8mb4 索引前缀 767 字节限制（必要时前缀索引 `oe(191)`）。
