# 客访管理 - 费用分析模块设计

> 本文档是《[01-主设计文档.md](01-主设计文档.md)》的补充模块，补齐"拜访投入"维度的费用记录与盈利分析。
> 需求来源：每次拜访产生的费用（样品费、招待费、差旅费等）需要逐笔记录，并按月/按客户汇总，与销售数据联动计算"总利益"。
> 公式核心：**总利益 = 累计拿货额 − 累计退货金 − 销售成本 − 累计拜访投入**
> **代码现状**（2026-10-29）：费用尚未落地到表；主设计文档中"累计拜访投入"指标（第五节）标注为 `SUM(expense_amount)`，但原设计已从 `visit_record` 移除了 `expense_type` / `expense_amount` 字段（4.3 节"相对原设计移除的字段"）；本文档通过**独立费用明细表**补回该能力。

---

## 一、模块定位与范围

**解决的问题**：业务员每次跑客户可能发生样品费、油费、高速费、招待费等多项支出，但这些费用散落在个人报销或 Excel 里，无法与"这次拜访带来了多少订单"做归因比对。

**本期范围**：

| 能力 | 说明 |
| --- | --- |
| 费用录入 | 每次拜访可关联**多条消费项**（一样多），支持多条、多类型 |
| 费用分析页 | 按月汇总、按客户汇总、按费用类型汇总；与销售指标联动展示 |
| 客户详情页接入 | 客户详情 Tab 新增"费用投入"概览卡 |
| 公式计算 | 与销售数据（拿货额、退货、成本）联动算出"总利益" |

**本期不做**（推迟的能力）：

| 推迟项 | 原因 |
| --- | --- |
| 费用审批/报销流程 | 需要对接财务系统，本期只做记录不做审批 |
| 费用预算控制 | 需先有历史数据沉淀，再定预算阈值 |
| 业务员费用排名/绩效归因 | 依赖快照表与团队架构，复杂度较高 |
| 高德端费用自动同步 | 高德小程序费用字段本期未启用（主设计 4.3） |

## 二、数据模型设计

### 2.1 ER 关系

```
visit_record (拜访记录)  1 ──── N  visit_expense (费用明细)
visit_follow_record (跟进记录)  1 ──── N  visit_expense (费用明细)  [可选关联]
```

> 关联锚点选择：费用主要发生在**拜访时**，所以费用明细表以 `visit_record` 为主关联对象；但某些费用可能对应"跟进"而非"上门"（如电话沟通后的样品邮寄费），故预留 `visit_follow_record` 关联。**一条费用记录只能关联其中一个，不能同时关联**，用 `source_type` 区分。

### 2.2 费用明细表 `visit_expense`

表说明：客访-拜访费用明细表，一条记录代表**一笔具体消费**（如"2026-10-29 样品费 ¥320"）。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | 主键，自增 |
| `source_type` | TINYINT | 关联来源类型：1-拜访记录（visit_record） 2-跟进记录（visit_follow_record），非空 |
| `source_id` | BIGINT | 关联记录 ID（`visit_record.id` 或 `visit_follow_record.id`），非空 |
| `amap_customer_id` | VARCHAR(128) | 高德客户 POI 编码（冗余，用于按客户维度直接索引，避免每次 JOIN）→ `visit_amap_customer.amap_poi_id`，可空 |
| `expense_date` | DATE | 费用发生日期，非空（默认取关联拜访/跟进记录的时间；若手动录入无关联则取录入日期） |
| `expense_type` | VARCHAR(50) | 费用类型，非空，自由填写文本（业务自行约定分类口径） |
| `amount` | DECIMAL(12, 2) | 金额（元），非空，> 0 |
| `description` | VARCHAR(500) | 费用说明/备注 |
| `recorder_id` | INT | 录入人 ID → `crmapp_users.id`，非空 |
| `status` | TINYINT | 1-正常 0-作废，默认 1，非空 |
| `created_at` | DATETIME | 创建时间，默认当前时间 |
| `updated_at` | DATETIME | 更新时间，默认当前时间并随更新自动变更 |

**索引与约束**：

| 类型 | 索引名 | 字段 | 说明 |
| --- | --- | --- | --- |
| 主键 | PRIMARY | `id` | 物理主键 |
| 普通索引 | `idx_source` | `source_type, source_id` | 按关联记录查费用（1:N 正向） |
| 普通索引 | `idx_amap_customer_date` | `amap_customer_id, expense_date` | 客户维度 + 时间窗口查询 |
| 普通索引 | `idx_expense_type` | `expense_type` | 费用类型汇总分析 |
| 普通索引 | `idx_recorder` | `recorder_id` | 业务员个人费用查询 |
| 表字符集 | — | — | `utf8mb4 / utf8mb4_unicode_ci` |

> **关于唯一键**：费用记录的幂等性由业务流程保证（录入即真实发生，不做自动去重），故不设业务唯一键；重复录入通过前端提示 + 人工校验发现。

### 2.3 费用类型说明（自由填写文本）

`expense_type` 是 `VARCHAR(50)` 自由文本字段，**不做枚举校验、不做字典表**，前端直接给一个输入框，业务员自己填。

**理由**：费用类型的分类口径在实际使用中变化快——同一个业务员可能某次把"咖啡钱"填"招待费"、下次填"茶水费"；不同业务员对同一笔钱怎么分类也不一样。强行枚举反而导致录入麻烦、或者业务员填了"其他"然后在 description 里补具体内容，让类型字段失去意义。本期不做硬性分类约束，让数据先沉淀，后续有了一定量的费用数据后，再根据实际分布反推"要不要做类型规范"（比如跑个 `GROUP BY expense_type ORDER BY COUNT DESC` 看看 top 类型是什么、是不是需要统一）。

**类型汇总统计**：费用分析页"费用类型占比"饼图直接 `GROUP BY expense_type`，即使同一个含义出现了"招待费"和"餐饮招待"两条也如实展示——这反而能暴露"类型口径不统一"的情况，倒逼业务自发规范。

### 2.4 字段冗余说明

`amap_customer_id` 在 `visit_record` / `visit_follow_record` 中可以通过 JOIN 拿到，这里冗余是为了：

1. **直接索引查询**：费用分析页按"客户"或"月份"筛选时不需要跨表 JOIN，降低查询复杂度
2. **关联断裂时仍可统计**：若后续 `visit_record` 被作废或客户解绑，费用记录本身仍有客户归属信息，不会变成"孤儿数据"
3. **销售数据求和**：费用表没有冗余 `partner_id`，汇总销售指标时通过 `amap_customer_id → visit_customer_relation → partner_id` 桥接查询（复用客户详情页已有路径）

## 三、业务流程

### 3.1 费用录入入口

| 入口 | 关联对象 | 流程 |
| --- | --- | --- |
| 拜访历史时间轴 | `visit_record` | 在某条拜访记录上点击"添加费用" → 弹出费用输入表单，`source_type=1, source_id=visit_record.id` 自动填充，客户信息自动带入 |
| 跟进记录时间轴 | `visit_follow_record` | 在某条跟进记录上点击"添加费用" → `source_type=2, source_id=visit_follow_record.id` 自动填充 |
| 费用分析页独立录入 | 可选关联或无关联 | 手动选择客户 + 可选关联某条拜访/跟进记录，支持"单独记账"场景（如月末统一补录） |

### 3.2 费用录入形式（三种入口，按需选用）

根据不同场景，费用录入提供三种形式，覆盖"在拜访记录上顺手记一笔"到"月末批量补录"。

#### 形式 A：拜访时间轴内快速添加（最常用）

客户详情页 → 拜访历史 Tab → 某条拜访记录卡片下方直接展示该次拜访的已有费用（小标签 + 金额汇总），右侧一个醒目的"+ 加费用"按钮。点击按钮弹出 **layer modal** 小表单，录入后保存即回写卡片。

```
拜访时间轴某条记录：
┌──────────────────────────────────────┐
│ 经  zhangyw  2026-10-29 10:32      │
│ 主推新款陶瓷刹车片...                │
│                                      │
│ 💰 本次费用：样品费 ¥320 · 招待费 ¥180  [+ 加费用] │
└──────────────────────────────────────┘
```

Modal 表单（单条录入，弹窗不大，3 秒完成）：
```
┌──────────────────────────┐
│ 添加费用（华泰汽修 10/29） │
│ 类型：[样品费]            │
│ 金额：[320.00]            │
│ 说明：[陶瓷刹车片2套]     │
│                           │
│      [取消]  [保存]       │
└──────────────────────────┘
```

**特点**：`source_type`/`source_id`/`amap_customer_id`/`expense_date` 全部自动带入，业务员只填最核心的三项（类型、金额、说明）。

#### 形式 B：费用分析页批量快速录入（月末补录多笔）

费用分析页顶部提供**可展开的批量录入区**，一次录入多笔费用，点"全部保存"一次性提交。

```
┌─────────────────────────────────────────────────────────┐
│ ▼ 批量录入（可展开/收起）                                │
│                                                         │
│ 客户：[华泰汽修 ▼]  日期：[2026-10-29]  关联：[拜访▼]   │
│                                                         │
│ ┌──────┬──────────┬──────────┬──────────────┐            │
│ │ #    │ 费用类型  │ 金额      │ 说明          │ [删]   │
│ ├──────┼──────────┼──────────┼──────────────┤            │
│ │ 1    │ 样品费   │ 320.00   │ 陶瓷刹车片2套  │ ✕      │
│ │ 2    │ 招待费   │ 180.00   │ 师傅吃饭      │ ✕      │
│ │ 3    │ 差旅费   │ 65.00    │ 高速费+油费    │ ✕      │
│ └──────┴──────────┴──────────┴──────────────┘            │
│ [+ 再加一行]                       [全部保存] [清空]     │
└─────────────────────────────────────────────────────────┘
```

**交互**：
- 第一列"#"自动序号，金额自动求和显示在底部
- 空行自动校验（有类型就必须有金额），不完整的行高亮提示
- 保存全部走**一个 API 批量接口**（`POST /api/visit/expenses/batch`），后端一次事务提交
- 保存成功后自动清空表单，客户/关联/日期保持不变（方便继续录同一客户）

#### 形式 C：费用分析页独立单条录入

和形式 B 同一页面，在列表区域每行有"编辑/作废"操作；列表上方有"单独添加"按钮（弹出 Modal，即形式 A 的表单）。适合零散录入。

#### 三种形式的对比

| | 形式 A（时间轴内弹窗） | 形式 B（批量表格） | 形式 C（列表上按钮） |
| --- | --- | --- | --- |
| 适用场景 | 拜访完客户顺手记一笔 | 月末统一补录/一次拜访多笔 | 零散补录 |
| 效率 | 单条 3 秒 | 一次 5-10 笔 2 分钟 | 单条 5 秒 |
| 客户/关联带入 | 自动全带 | 手动选一次，多行共用 | 手动全选 |
| API | `POST /api/visit/expenses` 单条 | `POST /api/visit/expenses/batch` 批量 | 同形式 A |

> 本期**必须做**形式 A 和形式 B；形式 C 就是形式 A 的入口不同，复用同一 Modal。后端只需一个单条 POST 接口 + 一个批量 POST 接口。

### 3.3 费用编辑与作废

| 操作 | 规则 |
| --- | --- |
| 编辑 | 费用记录可编辑金额、类型、说明；**客户归属、关联记录、录入人不可改**（保审计） |
| 作废 | 软作废（`status=0`），不物理删除；作废后不计入任何费用统计 |
| 恢复 | 作废记录可恢复为正常（`status=1`），前端需有筛选入口"已作废" |

> 拜访记录本身可以作废（`visit_record.status=0`），此时其关联的费用记录**不自动作废**——因为费用真实发生过，拜访作废只是拜访本身的业务状态变更。费用作废独立管理。

## 四、费用分析页设计

### 4.0 页面定位与路由

费用分析页是**页面级独立 tab**，与现有"客户列表 / 客户详情 / 设置"同级，通过主页面顶部 `#header-tabs` 切换进入。

```
// visit_manage_main_web.html 路由配置 PAGES 数组新增一项：
{ key: 'expense', title: '费用分析', file: 'expense_analysis.html' }

// 路由 hash：#/expense
// 页面片段文件：templates/visit_manage/views/expense_analysis.html
```

> 形式 A（拜访时间轴内加费用）的入口在客户详情页 → 拜访历史 Tab，不在费用分析页；费用分析页承载形式 B（批量录入）、形式 C（列表录入）和所有分析视图。

### 4.2 总利益公式口径拆解

| 公式项 | 数据源 | 口径说明 |
| --- | --- | --- |
| **累计拿货额** | `sales_order_history` 常规订单（`order_type_id=1`） | 订单级聚合 `SUM(total_price)`，按客户集合求和；与主设计文档 5 节指标卡口径一致 |
| **累计退货金** | `sales_order_history` 退货订单（`order_type_id=2`） | 订单级聚合 `SUM(total_price)`，退货单单独汇总，不抵减拿货额（退货率单独算） |
| **销售成本** | `crmapp_compare_summary.cost_price × sales_order_history.quantity` | 明细级 JOIN 后聚合，与 06-利润指标设计口径一致；按现行成本估算，标注 sub |
| **累计拜访投入** | `visit_expense.amount`（`status=1`） | `SUM(amount)`，本期时间窗口内的费用合计；可按月/按年/按客户任意切片 |
| **总利益** | = 累计拿货额 − 累计退货金 − 销售成本 − 累计拜访投入 | **负数代表投入超过产出**，前端标红警示 |

**时间窗口**：公式中的"累计"默认是**当前筛选窗口内**（月度视图 → 本月；年度视图 → 本年），不是"全部历史累计"。否则新客户刚跑几次拜访，总利益必然为负，没有对比意义。

**投入产出比**（辅助指标）：
```
投入产出比 = 累计拿货额 / 累计拜访投入
```
- 比值 > 10x → 投入高效
- 比值 3~10x → 正常
- 比值 < 3x → 投入偏低效（需关注是否新客孵化期、还是真的产出少）
- 拿货额为 0 → 不计算或显示 N/A

### 4.3 客户费用排名表

| 列 | 取数 |
| --- | --- |
| 客户名 | `visit_amap_customer.customer_name`（未绑 CRM 时用高德名；已绑显示 CRM 名优先） |
| 拜访次数 | `COUNT(visit_record WHERE amap_customer_id AND status=1 AND source_type=1)` |
| 费用合计 | `SUM(visit_expense.amount WHERE amap_customer_id AND status=1)` |
| 拿货额 | `SUM(sales_order_history.total_price)` 常规订单，通过 `amap_customer_id → visit_customer_relation → partner_id` 桥接查询 |
| 投入产出比 | 拿货额 ÷ 费用合计（拿货额=0 时不显示） |
| 总利益 | 拿货额 − 退货金 − 成本 − 费用合计 |

**排序**：默认按费用合计降序 → 找到投入最多的客户，先看这些客户的产出。

### 4.4 月度费用趋势图

X 轴：月份（近 12 个月）
左 Y 轴（柱状）：费用投入（蓝色柱）+ 拿货额（绿色柱）
右 Y 轴（折线）：总利益（橙色折线，负数标红）

**空月填充**：某月没有任何费用/订单 → 费用投入和拿货额显示 0，总利益也为 0，保持折线连续性。

SELECT
    SUM(amount)                                      AS total_expense,
    SUM(CASE WHEN expense_date >= :month_start
             THEN amount ELSE 0 END)                  AS month_expense,
    GROUP_CONCAT(CONCAT(expense_type, '¥', amount)
                 ORDER BY amount DESC SEPARATOR ' ')  AS type_breakdown
FROM visit_expense
WHERE amap_customer_id = :amap_poi_id
  AND status = 1;

## 八、DDL（建议 SQL 脚本）

```sql
CREATE TABLE IF NOT EXISTS visit_expense (
    id                  BIGINT          NOT NULL AUTO_INCREMENT COMMENT '主键',
    source_type         TINYINT         NOT NULL COMMENT '关联来源类型: 1-拜访记录(visit_record) 2-跟进记录(visit_follow_record)',
    source_id           BIGINT          NOT NULL COMMENT '关联记录ID',
    amap_customer_id    VARCHAR(128)    DEFAULT NULL COMMENT '高德客户POI编码(冗余,visit_amap_customer.amap_poi_id)',
    expense_date        DATE            NOT NULL COMMENT '费用发生日期',
    expense_type        VARCHAR(50)     NOT NULL COMMENT '费用类型(自由填写文本,不做枚举校验)',
    amount              DECIMAL(12, 2)  NOT NULL COMMENT '金额(元),>0',
    description         VARCHAR(500)    DEFAULT NULL COMMENT '费用说明/备注',
    recorder_id         INT             NOT NULL COMMENT '录入人ID(crmapp_users.id)',
    status              TINYINT         NOT NULL DEFAULT 1 COMMENT '1-正常 0-作废',
    created_at          DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at          DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (id),
    INDEX idx_source (source_type, source_id),
    INDEX idx_amap_customer_date (amap_customer_id, expense_date),
    INDEX idx_expense_type (expense_type),
    INDEX idx_recorder (recorder_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='客访-拜访费用明细表';
```

## 九、性能与技术风险

| # | 风险 | 应对 |
| --- | --- | --- |
| 1 | 费用表与销售表联合查询性能 | 客户费用排名/趋势需要 JOIN `sales_order_history` 聚合，复用 06-利润指标的订单级基表子查询，不在费用表层面做行级 JOIN；按月度聚合先在费用表内汇总再拼销售数据 |
| 2 | 冗余字段填充时机 | 录入时根据 `source_type/source_id` 反查客户归属并写入 `amap_customer_id`；若 `visit_record` 已作废，客户归属字段仍可从记录内读取，不受作废影响 |
| 3 | 独立录入无关联记录 | 允许 source_type/source_id 同时为空（此时必须显式传 `amap_customer_id`），用于月末补录等场景；需加校验：至少有一个关联或客户字段 |
| 4 | `source_id` 失效 | 关联的拜访/跟进记录被物理删除（visit_record 本期只允许作废、不允许物理删除；若后续加物理删除需加定期孤儿费用校验） |
| 5 | 费用类型口径不统一 | 自由填写会导致同一含义出现多种写法（"招待费"/"餐饮招待"/"吃饭"），`GROUP BY expense_type` 会拆散；费用分析页饼图如实展示，倒逼业务自发规范，后续数据量上来后可考虑加枚举约束 |
| 6 | 金额精度 | DECIMAL(12,2) 最大支持千万级年度投入（单客户），足够；与 `sales_order_history.total_price`（DECIMAL(18,2)）精度兼容 |
| 7 | 并发录入 | 业务员同时给同一客户录入多条费用，无唯一键冲突风险，MySQL InnoDB 行锁足够 |

## 十、与已有模块的关联变更

| 已有模块 | 变更 | 影响 |
| --- | --- | --- |
| **主设计文档 4.3** `visit_record` | 原设计从 visit_record 移除了 `expense_type/expense_amount` 字段 → 费用能力由本文档的 `visit_expense` 独立表承接 | 无数据迁移，新建表即可 |

| --- | --- | --- | --- |
